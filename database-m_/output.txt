--- 1. MYSQL (RDBMS) VS NOSQL ---
Ex 1.1 - RDBMS (MySQL) Normalized Relational Row with Foreign Key: User 101 -> Order $250.0
Ex 1.2 - Document NoSQL (MongoDB Hierarchical Embedded Document): {_id=obj_6619ef, name=Alice, addresses=[{city=New York, zip=10001}, {city=Austin, zip=73301}]}
Ex 1.3 - Key-Value NoSQL (Redis Session Store): {user: 'Alice', role: 'ADMIN', ttl: 3600}
Ex 1.4 - Scaling -> MySQL: Vertical (Read Replicas) | NoSQL: Horizontal Distributed Sharding
Ex 1.4 - Schema -> MySQL: Fixed/Strict DDL | NoSQL: Schema-less / Dynamic JSON
Ex 1.4 - Data Model -> MySQL: Relational Tables | NoSQL: Document, Key-Value, Columnar, Graph
Ex 1.4 - Transactions -> MySQL: ACID (Immediate) | NoSQL: BASE (Eventual Consistency)
Ex 1.5 - Polyglot Persistence: Use MySQL for payments, Redis for caching, MongoDB for product catalog, Cassandra for audit logs

--- 3. ACID VS BASE ---
Ex 3.1 - ACID Consistency Check: true
Ex 3.2 - BASE Soft State (Replicas divergent during sync window): Consistent=false
Ex 3.2 - BASE Eventual Consistency reached: Consistent=true (Replica=Value_V2)
Ex 3.3 - Focus -> ACID: Data Accuracy & Financial Precision | BASE: High Availability & Low Latency
Ex 3.3 - Schema -> ACID: Rigid relational schemas | BASE: Dynamic schema-less documents
Ex 3.3 - Consistency -> ACID: Immediate / Linearizable | BASE: Eventual / Tunable Quorum
Ex 3.3 - Transactions -> ACID: Heavyweight two-phase locking | BASE: Lightweight Saga / compensation
Ex 3.4 - CAP Theorem: ACID databases are CP (Consistency + Partition Tolerance); BASE databases are AP (Availability + Partition Tolerance)
Ex 3.5 - Tunable Consistency: Read/Write Quorum (W + R > N) turns an AP BASE database into a strongly consistent store

--- 7. DIFFERENCE BETWEEN WHERE AND HAVING ---
Ex 7.1 - WHERE (active = true) filtered out inactive Dave: count=4
Ex 7.2 - GROUP BY department averages: {Engineering=115000.0, HR=60000.0, Marketing=90000.0}
Ex 7.2 - HAVING AVG(salary) > 100,000 result: {Engineering=115000.0}
Ex 7.3 - Invalid SQL: 'SELECT dept FROM emp WHERE AVG(salary) > 5000' fails because WHERE evaluates before aggregation occurs!
Ex 7.4 - Standard Query: 'SELECT dept, AVG(salary) FROM emp WHERE active=1 GROUP BY dept HAVING AVG(salary) > 80000'
Ex 7.5 - Performance Tip: Always filter out rows in WHERE clause early to reduce the volume of rows fed into GROUP BY memory

--- 8. DELETE VS DROP VS TRUNCATE ---
Ex 8.1 - DROP -> DDL | Destroys table structure + data + metadata completely from DB catalog
Ex 8.1 - DELETE -> DML | Can use WHERE | Slow (Row-by-row Undo logs) | Rollbackable | Fires Triggers | Retains Auto-Increment
Ex 8.1 - TRUNCATE -> DDL | No WHERE clause | Ultra-Fast (Page deallocation) | Resets Auto-Increment to 1 | No Triggers
Ex 8.2 - DELETE with WHERE result: [Row_1, Row_3]
Ex 8.3 - TRUNCATE wiped data & reset autoIncrement: size=0, nextId=1
Ex 8.4 - DROP TABLE removed metadata definition from catalog: exists=false
Ex 8.5 - Gotcha: TRUNCATE fails if the table is referenced by an active FOREIGN KEY constraint in another table
